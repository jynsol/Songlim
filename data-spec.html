1. 핵심 결론

송림은 특정 플랫폼 하나의 API를 마스터 DB처럼 쓰면 안 된다. 송림 자체 Content ID를 중심으로, 카테고리별 복수 공급자의 식별자를 연결하는 구조가 가장 안전하다.

중요한 수정
초기 검토에서 생각했던 “알라딘을 책 메인, Spotify를 음반 메인” 구조는 프로덕션 핵심 의존성으로는 부적합하다. 알라딘 일반 OpenAPI는 영리 서비스 이용이 불가하고 별도 제휴가 필요하며, Spotify 신규 앱의 Extended Quota는 현재 매우 높은 진입 조건이 있다. 따라서 송림 MVP의 기본 설계는 이 둘 없이도 작동해야 한다.

2. 전체 데이터 수집 구조

외부 공유 / 이미지·목록 가져오기 / 직접 검색 → Input Parser → 후보 추출 → Provider Search → Entity Resolution → Confidence 판정 → 송림 Content → UserContent
원칙 01
AI는 검색어를 만든다
LLM이 최종 사실 DB가 되지 않는다. 제목·제작자·유형 후보를 구조화하는 데 사용한다.
원칙 02
외부 ID는 여러 개 보관한다
ISBN, MBID, ISRC, TMDB ID, KOBIS movieCd 등을 송림 내부 ID 밑에 연결한다.
원칙 03
낮은 신뢰도는 자동 병합 금지
동명이작·재발매·번역판 때문에 “비슷함”만으로 병합하지 않는다.
원칙 04
API 장애가 저장 실패가 되지 않게 한다
최소 제목·유형만으로 임시 Content를 만든 뒤 비동기로 보완할 수 있다.
원칙 05
여러 건은 Batch로 다룬다
장바구니·찜 목록 캡처처럼 한 화면에 여러 작품이 있을 때는 항목별 후보를 독립 검증한 뒤 한 번에 확인·저장한다.

3. 책 데이터

3.1 MVP 권장: Kakao Daum 책 검색 API

현재 공식 문서 기준 GET https://dapi.kakao.com/v3/search/book가 제공되며 REST API 키로 호출한다. 제목 검색과 정확도순 결과를 사용할 수 있고, 책 검색 일일 무료 쿼터는 30,000회다. 네이버 책 검색 API는 2026년 7월 31일 종료되어 후보에서 제외한다.

thumbnail_urlKakao목록·상세 이미지. 공개 출시 전 이미지 사용조건 재확인.

3.2 Google Books

보조 조회로 사용한다. 공식 API는 intitle:, inauthor:, isbn: 검색을 지원한다. Kakao 결과가 없거나 ISBN 교차검증이 필요할 때 적합하다.

3.3 알라딘은 “제휴 후” 사용

알라딘 OpenAPI 자체는 검색·상품 조회와 ISBN13 조회를 제공하지만, 공식 이용 안내상 도서 정보를 기반으로 하는 법인·기업·단체 서비스 및 영리 목적 서비스는 일반 OpenAPI 이용이 불가하다. 기업/제휴 경로는 별도로 존재하므로 구매 연계 BM을 붙일 시점에 제휴를 신청한다.

책 MVP 결론
Kakao → Google Books → 사용자 보정. 알라딘은 상품 구매 제휴가 성립한 뒤 공급자와 구매 링크 소스로 추가한다.

4. 음반 데이터

4.1 MVP 권장: MusicBrainz

MusicBrainz 핵심 DB에는 Artist, Release Group, Release, Recording, Label 등 음악 카탈로그 구조가 있고 핵심 데이터는 CC0다. 송림의 상위 콘텐츠는 ALBUM, 하위 일일 경험은 TRACK이므로 Release Group/Release와 Recording 구조를 매핑하기 좋다.

송림 필드MusicBrainz 매핑비고
album_titleRelease Group / Release name사용자에게는 대표 앨범 단위로 노출
artists[]Artist / artist-credit복수 아티스트 지원
release_group_mbidRelease Group MBID송림의 앨범 작품 단위에 가까움
release_mbidRelease MBID실제 판본·발매 구분
tracks[]Medium / Track / Recording오늘의 곡 제공
isrcRecording ISRC 관계트랙 식별 보조
cover_urlCover Art Archive권리 고지는 별도 검토. 없으면 placeholder 허용.

공개 Web Service는 평균 1회/초 제한이 있으므로 사용자가 검색할 때마다 여러 요청을 연쇄적으로 날리면 안 된다. 서버 캐시 + 요청 큐 + 검색 결과 재사용을 기본으로 하고, 성장 후에는 CC0 core dump를 자체 인덱싱하는 방향도 가능하다.

4.2 Cover Art Archive

Release/Release Group MBID로 대표 커버와 250/500/1200 썸네일을 조회할 수 있다. 공식 API 문서상 현재 별도 rate limit 규칙은 없지만, 이미지 자체의 권리는 서비스가 보증하지 않으므로 공개 상용 서비스에서는 법무·라이선스 검토가 필요하다.

4.3 Spotify는 핵심 의존성에서 제외

기술적으로 Search, Album, Track, ISRC/UPC 데이터는 매우 좋고 Client Credentials 방식의 서버 간 인증도 가능하다. 다만 2026년 현재 신규 Development Mode는 실험·개인 프로젝트 성격이며 앱 소유자 Premium 요건과 최대 5명의 인증 사용자 제한이 있다. Extended Quota는 법인, 출시 서비스, 최소 250k MAU 등 높은 기준을 명시한다. 따라서 초기 송림이 공개 사용자 대상으로 Spotify를 핵심 데이터 공급자로 삼는 구조는 현실적으로 위험하다.

음반 MVP 결론
MusicBrainz core metadata → Cover Art Archive → 필요 시 Spotify URL을 외부 링크로 보관. Spotify API는 내부 프로토타입 또는 향후 파트너 승인 후 보조 공급자로 추가한다.

5. 영화 데이터

5.1 TMDB

TMDB는 원제·번역 제목·대체 제목을 대상으로 영화 검색을 제공하고, 상세·크레딧·외부 ID까지 연결하기 쉬워 글로벌 영화 엔티티 매칭에 가장 적합하다. 다만 공식 FAQ에서 수익을 목적으로 하는 프로젝트는 commercial로 보며, 무료 developer API는 비상업 용도로 설명하고 있다. 송림은 상용 출시 전에 TMDB commercial licensing을 문의해야 한다.

5.2 KOBIS

영화진흥위원회 OpenAPI에는 영화 목록·영화 상세 조회가 존재하며 키 발급 후 REST/SOAP 방식으로 호출할 수 있다. 국내 개봉 영화명, 감독, 제작정보와 movieCd를 보완 식별자로 사용한다.

영화 MVP 결론
기술 검증에서는 TMDB + KOBIS가 가장 현실적이다. 다만 실제 상용 출시의 Go/No-Go 항목에 “TMDB 상업 사용 조건 확정”을 반드시 넣는다.

6. 외부 공유 유입 정책

송림의 지속 유입은 Instagram, Threads, 블로그, YouTube 등에서 발견한 콘텐츠 공유를 중심으로 하고, 첫 진입·대량 이전은 서점 장바구니·찜 목록·SNS 저장 화면 등의 이미지 가져오기를 보조 경로로 둔다. SNS를 데이터베이스처럼 크롤링하지 않고, 사용자가 명시적으로 전달한 URL·텍스트·이미지와 접근 가능한 공개 메타데이터를 단서로 정식 콘텐츠 DB에서 엔티티를 찾아 확정한다.

제품 약속
“공유하거나 가져오면 자동 식별을 우선 시도하고, 확실하지 않을 때만 확인받는다.”를 기본 약속으로 둔다. 임의의 SNS 게시물·스크린샷을 100% 자동 인식한다고 약속하지 않으며, 자동 식별 실패 시에도 후보 선택·제목 검색으로 저장을 완료할 수 있게 한다.

7. 이미지·목록 가져오기

사용자가 교보문고·알라딘 장바구니, 서점 보관함, OTT 찜 목록, SNS 저장 화면처럼 이미 쌓아둔 관심 콘텐츠를 스크린샷/사진으로 전달하면 여러 작품 후보를 한 번에 추출·정리한다. 이 경로는 첫날 빈 스크랩을 빠르게 채우는 온보딩 수단이며, 외부 공유는 이후 관심을 계속 쌓는 주 루프로 유지한다.

8. Save
- 기본 UserContent.status = INTERESTED
- 기존 UserContent가 있으면 중복 생성하지 않고 Source만 추가

7.3 자동 상태 추론 규칙

  • 장바구니·찜·보관함·보고 싶은 목록: 기본 INTERESTED.
  • “읽음/봤음/들었음/완료”가 화면에 명시되어 있고 작품 매칭 신뢰도도 높은 경우: EXPERIENCED 후보로 표시할 수 있으나 Batch Review에서 사용자가 확인한다.
  • 이미지 내용만으로 경험 여부가 불분명하면: 절대 EXPERIENCED로 자동 확정하지 않는다.
  • DISLIKE: 이미지에서 부정 반응이 명시되어도 자동 저장하지 않고 사용자 선택으로만 만든다.

7.4 온보딩과 연결

신규 가입 → “10개 직접 선택” 또는 “저장해둔 콘텐츠 가져오기” → 유효 취향 신호 누적 → 최소 10개 신호 충족 → 송림 시작
  • 온보딩의 최소 기준은 유효 취향 신호 10개로 통일한다.
  • 직접 선택 1건과 정상 매칭된 가져오기 1건을 각각 1개 신호로 계산해 혼합 가능하게 한다. 예: 직접 선택 4개 + 가져오기 6개.
  • 가져오기 콘텐츠는 대부분 INTERESTED 신호이므로, 추천 품질을 위해 이후 사용 중 가벼운 평가를 추가 수집할 수 있다.
  • 가져오기는 온보딩 이후에도 스크랩 화면에서 다시 실행할 수 있어야 한다.

7.6 개인정보·원본 이미지 처리

MVP 권장 정책
장바구니·주문 화면에는 사용자명, 주문정보, 금액 등 불필요한 정보가 함께 찍힐 수 있다. 분석 대상은 작품 식별에 필요한 영역으로 최소화하고, 원본 이미지는 콘텐츠 식별 후 기본적으로 장기 보관하지 않는다. 송림 DB에는 정규화된 Content, 출처 유형, 필요한 최소 Evidence만 남긴다. 원본 보관이 필요한 기능을 추후 만들 경우 별도 동의와 보관기간을 정의한다.

7.7 검증 지표

지표정의초기 목표/판단
이미지 처리 성공률선택한 이미지에서 1개 이상의 유효 콘텐츠 후보를 만든 비율출처 유형별 측정
항목 추출 Recall이미지에 실제 존재하는 작품 중 후보로 생성한 비율장바구니/목록 화면을 우선 고도화
항목 정답률자동 확정 또는 첫 후보가 실제 작품과 일치하는 비율오답 자동 저장률 우선 관리
사용자 보정률항목별 후보 변경·제목 검색이 발생한 비율낮을수록 좋음
Batch 저장 완료율가져오기 시작 후 최소 1건 이상 UserContent 저장까지 완료한 비율95%+ 목표 제안
항목당 처리 시간분석 시작부터 Batch Review 표시까지의 시간 / 유효 항목 수실기기 측정 후 기준 확정

기술 검증은 “아무 이미지나 잘 읽는가”보다 사용자가 실제로 많이 가져올 화면 유형을 먼저 정해 출처별 성능을 관리한다. 초기에는 책 장바구니·보관함 캡처를 가장 먼저 고정 샘플로 만든다.

8. SNS·웹 유입 식별 파이프라인

송림의 핵심 기술은 “SNS를 긁는 것”이 아니라 불완전한 공유 단서를 실제 콘텐츠 엔티티로 안전하게 변환하는 것이다. 정확도는 단일 AI 호출이 아니라 여러 증거를 합쳐 올린다.

7.1 처리 순서

1. Share Input
- source_app
- source_url
- shared_text
- captured_at

2. Direct Parser
- URL host / known provider ID
- page title / OG metadata
- JSON-LD / schema.org (공개된 경우)

3. Candidate Extraction
- type_candidate: BOOK | ALBUM | MOVIE
- title_candidate
- creator_candidate
- year_candidate?
- evidence[]

4. Context Enrichment
- 공개 웹/블로그 문맥
- 검색 가능한 제목/설명 단서
- 원천 서비스의 공개 메타정보

5. Provider Verification
- BOOK  → Kakao Book → Google Books
- ALBUM → MusicBrainz → Cover Art / 보조 공급자
- MOVIE → TMDB → KOBIS

6. Entity Resolution
- 강한 식별자 + 제목 + 제작자 + 연도 교차검증

7. Decision
- HIGH   → 자동 저장
- MEDIUM → 후보 1개 또는 2~3개 1탭 확인
- LOW    → 화면에서 찾기 / 제목 검색

8. Feedback
- 사용자의 정정·선택 결과를 SourceEvidence와 MatchLog에 기록

이미지·목록 가져오기는 위 Share Input 파이프라인과 별도 입력 어댑터를 사용하지만, Candidate Extraction 이후 Provider Verification → Entity Resolution → Decision → Feedback은 동일한 공통 파이프라인을 재사용한다.

7.2 AI 사용 원칙

  • AI는 존재하지 않는 콘텐츠를 만들어 DB에 넣지 않는다.
  • 공유 문맥에서 타입·제목·제작자 후보를 추출하고, 여러 실제 DB 후보를 랭킹하는 역할로 제한한다.
  • 최종 자동 확정은 외부 DB에서 실제 엔티티가 확인되고 증거 점수가 기준을 넘은 경우만 허용한다.
  • 작품명이 없는 “박찬욱 작품 중 이게 제일 좋음” 같은 문장은 사람 이름만으로 특정 영화를 추측 저장하지 않는다.

7.3 증거 기반 점수 예시

증거예시 가중치의미
표준 식별자 직접 확보즉시 높은 신뢰ISBN, MBID/ISRC, TMDB/KOBIS ID 등
공유 텍스트 제목 정확 일치+35작품명이 명시됨
주 제작자 정확 일치+25동명 작품 오탐 감소
페이지 title/OG 제목 일치+20웹 문맥의 직접 증거
외부 DB의 제목+제작자 조합 일치+30실제 엔티티 존재 검증
제목만 일치 / 제작자 불일치-30자동 확정 금지 방향

가중치는 초기 설계값이며 실제 150건 이상 테스트 결과로 조정한다. 중요한 목표는 자동화율 자체보다 오답 자동 저장률을 낮추는 것이다.

이미지 분석도 실패카테고리 + 제목 검색최소 입력으로 저장 완료
핵심 KPI
① 자동 식별 성공률 ② 후보 생성 성공률 ③ 자동 확정률 ④ 사용자 보정률 ⑤ 오답 자동 저장률 ⑥ 공유 시작→저장 완료율 ⑦ 저장 완료 시간. 오답 자동 저장률은 1~2% 이하를 초기 품질 목표로 두고, 자동 식별이 실패해도 최종 저장 완료율은 최대한 100%에 가깝게 만든다.

9. 직접 기록·검색 기반 메타데이터 자동완성

송림은 외부 공유뿐 아니라 독서·음반·영화 기록 앱처럼 직접 콘텐츠를 추가하는 경로를 제공한다. 사용자는 제목 몇 글자만 입력하고 후보를 선택하며, 저자·아티스트·감독·출판사·발매일·표지·외부 식별자 등은 Provider 검색 결과로 자동완성한다.

원칙
사용자가 메타데이터를 일일이 입력하게 하지 않는다. 직접 기록은 “검색어 입력 → 후보 선택 → 자동완성 → 상태 저장”의 짧은 흐름으로 처리하고, 외부 공유와 동일한 Content 엔티티에 연결한다.

8.1 기본 UX

제목 입력 → 콘텐츠 유형 추정/선택 → Provider 검색 → 후보 3~5개 → 1탭 선택 → 메타데이터 자동완성 → UserContent 상태 저장
유형사용자 입력 예자동완성 항목후보 구분 기준
책채식주의자저자, 출판사, 출간일, ISBN, 표지, 설명제목 + 저자 + 출판사/판본
음반In Rainbows아티스트, 발매일, 커버, 트랙 수/목록, MBID 등앨범명 + 아티스트 + 발매연도
영화헤어질 결심감독, 개봉연도, 포스터, 원제, 외부 ID제목 + 감독 + 개봉연도

8.2 책은 작품(Work)과 판본(Edition)을 분리 가능하게 설계

동일 작품이 여러 출판사·번역·개정판으로 존재하므로 사용자 경험은 작품 중심으로 단순하게 보여주되, 내부 데이터는 판본을 구분할 수 있게 설계한다. MVP에서는 ISBN 단위 Provider 레코드를 우선 저장하고, 정규화된 제목·저자 기준으로 동일 작품 후보를 묶을 수 있도록 work_key 또는 별도 Work 엔티티 확장 여지를 둔다.

Work: 데미안 / 헤르만 헤세
 ├─ Edition A: 민음사 / ISBN ...
 ├─ Edition B: 문예출판사 / ISBN ...
 └─ Edition C: 기타 출판사 / ISBN ...

MVP에서 판본 선택을 강제하지 않는다. 사용자가 특정 ISBN·서점 링크에서 유입된 경우에는 해당 판본을 연결하고, 제목 검색만 한 경우에는 대표 후보를 선택하게 한다.

8.3 외부 공유와 직접 기록은 같은 데이터로 합친다

직접 기록으로 생성된 콘텐츠와 Instagram·Threads·블로그·서점 공유로 생성된 콘텐츠를 별도 목록으로 관리하지 않는다. ProviderIdentifier와 정규화 필드를 이용해 동일 Content로 매칭하고, 사용자의 상태만 UserContent에서 관리한다.

직접 기록검색어 → Provider 후보 → Content → UserContent
외부 공유Source → 후보 추출 → Provider 검증 → Content → UserContent
중복 시새 Content를 만들지 않고 기존 Content에 Source/ProviderIdentifier만 추가

8.4 자동 확정보다 후보 선택을 우선

제목이 유일하고 Provider 결과가 명확할 때는 자동 선택할 수 있지만, 동명 작품·여러 판본·리마스터/재발매처럼 복수 후보가 존재하면 자동 확정하지 않는다. 사용자가 후보 카드 1개를 탭하면 필요한 메타데이터가 모두 채워지는 방식으로 정확도와 입력 편의성을 함께 확보한다.

11. 동일 콘텐츠 매칭 규칙

10.1 강한 식별자 우선

  • 책: ISBN13 정확 일치 → 동일 판본
  • 음반: MusicBrainz Release Group MBID 정확 일치 → 동일 앨범 작품. Release MBID는 판본 구분.
  • 트랙: Recording MBID 또는 ISRC + 아티스트 보조
  • 영화: TMDB ID 또는 KOBIS movieCd 정확 일치

10.2 식별자가 없을 때

단계비교 요소처리
A정규화 제목 + 주 제작자 정확 일치연도/출판사/발매일 확인 후 높은 신뢰도
B제목 유사 + 제작자 정확 + 연도 근접후보 자동 확정 가능하나 로그 남김
C제목만 유사자동 병합 금지, 후보 확인
D공급자 검색 실패USER_ONLY 임시 엔티티 생성 후 추후 보완

10.3 Confidence

  • 0.90 이상 + 상충 증거 없음: 자동 저장
  • 0.65~0.89: 후보 1~3개 확인
  • 0.65 미만 또는 후보 충돌: 화면에서 찾기 / 제목 검색

Confidence는 LLM의 자기평가값이 아니라 SourceEvidence와 Provider 검증 결과를 조합한 점수로 계산한다. 임계값은 초기값이며 실제 사용자 보정 로그로 재조정한다. 자동 확정률보다 오답 자동 저장률을 우선 관리한다.

11.4 이미지 Batch 중복·매칭

  • 한 이미지 안에서 같은 작품이 반복 검출되면 먼저 ImportCandidate 단계에서 묶는다.
  • 여러 이미지에서 같은 작품이 검출되어도 기존 Content/UserContent를 재사용하고 SourceEvidence만 추가한다.
  • Batch 안의 한 항목이 오답이어도 다른 고신뢰 항목 저장을 막지 않는다.
  • 낮은 신뢰도 항목은 Batch Review에서 제외할 수 있으며, 전체 Batch를 실패 처리하지 않는다.

12.1 실제 작동 검증용 샘플 세트

개발자가 API 키를 발급받으면 임의 검색어가 아니라 아래처럼 정답을 이미 아는 고정 샘플로 자동화 테스트를 만든다.

  • 콘텐츠 DB 품질: 책 50종, 음반 50종, 영화 50종을 별도 정답 세트로 유지
  • SNS/웹 유입 실증: Instagram 50건 + Threads 30건 + 블로그/기사 30건 + YouTube·서점·기타 40건 = 150건
  • 각 공유 샘플에 실제 작품 정답, Share Sheet payload, 추출 증거, 후보 목록, 최종 선택, 사용자 보정 여부를 기록
  • 출처별 자동 식별률·후보 생성률·오답 자동 저장률·최종 저장 완료율·완료 시간을 각각 계산

전체 평균만 보지 않는다. Instagram/Threads처럼 송림의 핵심 유입 채널은 별도 Go/No-Go 지표로 관리한다.

13.2 이미지·목록 가져오기 고정 샘플

초기에는 실제 사용 가능성이 높은 스크린샷 50장을 정답 세트로 만든다. 이미지 단위가 아니라 이미지 안의 작품 항목 단위로 정답을 기록한다.

  • 서점 장바구니·보관함 20장
  • 책 추천/읽고 싶은 목록 10장
  • OTT·영화 찜 목록 10장
  • Instagram/Threads 등 SNS 스크린샷 10장
  • 각 이미지별 실제 작품 수, 추출 작품 수, 정답 매칭 수, 오답 자동확정 수, 사용자 보정 수를 기록
  • 장바구니/정형 목록과 SNS/비정형 이미지는 별도 성공률로 관리

14. MVP 구현 순서

  1. Content / ProviderIdentifier / Source / ImportBatch / SourceAsset / ImportCandidate / SourceEvidence / MatchLog / UserContent 스키마부터 확정
  2. 온보딩 신호 규칙 구현: 직접 취향 응답 + 정상 매칭된 가져오기 항목을 합산해 최소 10개 신호 충족
  3. iOS 사진 선택/스크린샷 가져오기 입력 + Batch Review 기본 화면 구현
  4. 책 장바구니·보관함 캡처 1차 vertical slice: 이미지 단서 추출 → Kakao 책 검색 → Google Books fallback → 다건 저장
  5. 직접 기록 검색: 제목 입력 → 카테고리별 Provider 후보 → 1탭 선택 → 메타데이터 자동완성 → 기존 Content와 중복 병합
  6. Kakao 책 검색 API 연동 + Google Books fallback
  7. MusicBrainz 검색·Release Group/Release 매핑 + 요청 큐·캐시
  8. Cover Art Archive 커버 연결, 커버 없을 때 placeholder 처리
  9. TMDB 기술 연동 샘플 + KOBIS 보조. 동시에 TMDB 상업 라이선스 문의
  10. iPhone 실제 Share Sheet payload 로거 구현 → Instagram·Threads·블로그·YouTube 150건 수집
  11. Share Sheet 입력 파서: source_url / shared_text / source_app 저장
  12. OG / JSON-LD 파서와 후보 추출기
  13. 공통 Candidate Extraction / Provider Verification / Entity Resolution 모듈로 Share와 Import 입력을 통합
  14. AI는 BOOK/ALBUM/MOVIE + title + creator 후보 구조화 및 후보 랭킹에만 사용
  15. Provider 검색 결과 점수화 → 자동 확정 / 후보 확인 / 직접 수정
  16. 수정 이력을 SourceEvidence/MatchLog/ImportCandidate에 저장하여 매칭 룰 개선
  17. 출처별 성공률 대시보드: Share와 Screenshot Import를 분리하여 자동 식별률, 후보 생성률, 보정률, 오답 자동 저장률, 최종 저장 완료율, 저장 완료 시간 관리
MVP Go 기준 제안
Share Sheet와 Screenshot Import를 같은 평균으로 섞지 않는다. 책 장바구니·보관함 같은 정형 이미지에서는 항목 단위 정답률과 최종 저장 완료율을 먼저 높이고, SNS 비정형 이미지는 후보 확인까지 포함한 완료율을 우선 관리한다. 자동 저장 오답률은 1~2% 이하를 최우선 품질 목표로 유지한다.
