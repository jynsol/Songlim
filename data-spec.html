중요한 수정
초기 검토에서 생각했던 “알라딘을 책 메인, Spotify를 음반 메인” 구조는 프로덕션 핵심 의존성으로는 부적합하다. 알라딘 일반 OpenAPI는 영리 서비스 이용이 불가하고 별도 제휴가 필요하며, Spotify 신규 앱의 Extended Quota는 현재 매우 높은 진입 조건이 있다. 따라서 송림 MVP의 기본 설계는 이 둘 없이도 작동해야 한다.
기능정의서 정합성 기준
송림의 콘텐츠 유입은 세 경로로 통일한다. ① 외부 공유: 새롭게 발견한 콘텐츠를 계속 쌓는 기본 루프 ② 이미지 가져오기: 장바구니·찜 목록·SNS 저장 화면 등 이미 쌓인 관심을 여러 건 한 번에 옮기는 경로 ③ 직접 검색: 사용자가 제목을 찾아 직접 추가하거나 자동화 실패를 보완하는 확실한 경로. 세 경로 모두 최종적으로 동일한 Content / UserContent를 사용한다.

보조 조회로 사용한다. 공식 API는 intitle:, inauthor:, isbn: 검색을 지원한다. Kakao 결과가 없거나 ISBN 교차검증이 필요할 때 적합하다.

3.3 알라딘은 “제휴 후” 사용

알라딘 OpenAPI 자체는 검색·상품 조회와 ISBN13 조회를 제공하지만, 공식 이용 안내상 도서 정보를 기반으로 하는 법인·기업·단체 서비스 및 영리 목적 서비스는 일반 OpenAPI 이용이 불가하다. 기업/제휴 경로는 별도로 존재하므로 구매 연계 BM을 붙일 시점에 제휴를 신청한다.

4.2 Cover Art Archive

Release/Release Group MBID로 대표 커버와 250/500/1200 썸네일을 조회할 수 있다. 공식 API 문서상 현재 별도 rate limit 규칙은 없지만, 이미지 자체의 권리는 서비스가 보증하지 않으므로 공개 상용 서비스에서는 법무·라이선스 검토가 필요하다.

4.3 Spotify는 핵심 의존성에서 제외

기술적으로 Search, Album, Track, ISRC/UPC 데이터는 매우 좋고 Client Credentials 방식의 서버 간 인증도 가능하다. 다만 2026년 현재 신규 Development Mode는 실험·개인 프로젝트 성격이며 앱 소유자 Premium 요건과 최대 5명의 인증 사용자 제한이 있다. Extended Quota는 법인, 출시 서비스, 최소 250k MAU 등 높은 기준을 명시한다. 따라서 초기 송림이 공개 사용자 대상으로 Spotify를 핵심 데이터 공급자로 삼는 구조는 현실적으로 위험하다.

음반 MVP 결론
MusicBrainz core metadata → Cover Art Archive → 필요 시 Spotify URL을 외부 링크로 보관. Spotify API는 내부 프로토타입 또는 향후 파트너 승인 후 보조 공급자로 추가한다.

5. 영화 데이터

5.1 TMDB

TMDB는 원제·번역 제목·대체 제목을 대상으로 영화 검색을 제공하고, 상세·크레딧·외부 ID까지 연결하기 쉬워 글로벌 영화 엔티티 매칭에 가장 적합하다. 다만 공식 FAQ에서 수익을 목적으로 하는 프로젝트는 commercial로 보며, 무료 developer API는 비상업 용도로 설명하고 있다. 송림은 상용 출시 전에 TMDB commercial licensing을 문의해야 한다.

5.2 KOBIS

영화진흥위원회 OpenAPI에는 영화 목록·영화 상세 조회가 존재하며 키 발급 후 REST/SOAP 방식으로 호출할 수 있다. 국내 개봉 영화명, 감독, 제작정보와 movieCd를 보완 식별자로 사용한다.

6. 외부 공유 유입 정책

송림의 지속 유입은 Instagram, Threads, 블로그, YouTube 등에서 발견한 콘텐츠 공유를 중심으로 하고, 첫 진입·대량 이전은 서점 장바구니·찜 목록·SNS 저장 화면 등의 이미지 가져오기를 보조 경로로 둔다. SNS를 데이터베이스처럼 크롤링하지 않고, 사용자가 명시적으로 전달한 URL·텍스트·이미지와 접근 가능한 공개 메타데이터를 단서로 정식 콘텐츠 DB에서 엔티티를 찾아 확정한다.

제품·저장 원칙
외부 공유는 새롭게 발견한 콘텐츠를 계속 쌓는 기본 루프다. 고신뢰 결과라도 “매칭 자동 확정”과 “UserContent 저장”은 구분한다. 고신뢰는 SHARE-02에서 인식 결과를 보여주고, 확인이 필요한 경우 SHARE-03에서 후보 선택·최소 정정을 거친다. 신규 저장 상태는 INTERESTED이며, 이미 같은 content_id가 있으면 새 UserContent를 만들지 않는다.

- 온보딩 진입이면 저장 확정 건수를 valid_signal_count에 반영

7.3 가져오기 저장 상태 규칙

  • 신규 가져오기 항목: IMPORT-02에서 저장 확정 시 항상 INTERESTED로 생성한다.
  • 이미 존재하는 동일 콘텐츠: 새 UserContent를 만들지 않고 Source/Import evidence를 추가하며, 서로 다른 시점의 의도적 가져오기라면 save_count +1 한다. 기존 상태는 자동 변경하지 않는다.
  • 특히 EXPERIENCED: 장바구니·찜 목록을 다시 가져와도 INTERESTED로 되돌리지 않는다.
  • 이미지 안의 “읽음/봤음/완료” 문구: MVP 가져오기 상태를 자동 EXPERIENCED로 만들기 위한 근거로 사용하지 않는다. 경험 여부는 기능정의서의 명시적 사용자 행동으로 관리한다.
  • DISLIKE: 가져오기에서 자동 추론하지 않는다.

7.4 온보딩과 연결

신규 가입 → 10개 직접 선택 또는 저장 콘텐츠 가져오기 → 직접 응답 + 가져오기 저장 확정 항목 합산 → 유효 취향 신호 10개 이상 → TODAY-01
  • 직접 선택: 관심 있음 / 경험함 / 싫음의 유효 응답 1건 = 신호 1개. 건너뛰기는 저장·카운트하지 않는다.
  • 가져오기: IMPORT-02에서 실제 저장 확정한 신규/기존 콘텐츠 1건 = 신호 1개. 가져오기 항목의 신규 상태는 INTERESTED다.
  • 혼합: 두 경로를 합산한다. 예: 직접 선택 4개 + 가져오기 확정 6개 = 10개.
  • 이어하기: 온보딩 중 이탈하면 현재 유효 신호 수와 진행 위치를 저장하고 다음 진입에서 이어간다.
  • 완료: 10개 이상이면 별도 완료 화면 없이 TODAY-01로 이동할 수 있다.

7.6 개인정보·원본 이미지 처리

MVP 권장 정책
장바구니·주문 화면에는 사용자명, 주문정보, 금액 등 불필요한 정보가 함께 찍힐 수 있다. 분석 대상은 작품 식별에 필요한 영역으로 최소화하고, 원본 이미지는 콘텐츠 식별 후 기본적으로 장기 보관하지 않는다. 송림 DB에는 정규화된 Content, 출처 유형, 필요한 최소 Evidence만 남긴다. 원본 보관이 필요한 기능을 추후 만들 경우 별도 동의와 보관기간을 정의한다.

8. SNS·웹 유입 식별 파이프라인

송림의 핵심 기술은 “SNS를 긁는 것”이 아니라 불완전한 공유 단서를 실제 콘텐츠 엔티티로 안전하게 변환하는 것이다. 정확도는 단일 AI 호출이 아니라 여러 증거를 합쳐 올린다.

8.1 처리 순서

1. Share Input
- source_app
- source_url
- shared_text
- captured_at

2. Direct Parser
- URL host / known provider ID
- page title / OG metadata
- JSON-LD / schema.org (공개된 경우)

3. Candidate Extraction
- type_candidate: BOOK | ALBUM | MOVIE
- title_candidate
- creator_candidate
- year_candidate?
- evidence[]

4. Context Enrichment
- 공개 웹/블로그 문맥
- 검색 가능한 제목/설명 단서
- 원천 서비스의 공개 메타정보

5. Provider Verification
- BOOK  → Kakao Book → Google Books
- ALBUM → MusicBrainz → Cover Art / 보조 공급자
- MOVIE → TMDB → KOBIS

6. Entity Resolution
- 강한 식별자 + 제목 + 제작자 + 연도 교차검증

7. Match Decision
- HIGH   → canonical 매칭 자동 확정 → SHARE-02
- MEDIUM → 후보 1개 또는 2~3개 → SHARE-03 사용자 확인
- LOW    → 직접 검색 / 최소 수정 → SHARE-03

8. Feedback
- 사용자의 정정·선택 결과를 SourceEvidence와 MatchLog에 기록
매칭 판정과 저장 행위 분리
HIGH는 “정답 콘텐츠를 자동으로 골랐다”는 뜻이지 UserContent를 즉시 무조건 생성한다는 뜻이 아니다. 기능정의서 기준으로 외부 공유는 SHARE-02에서 결과를 보여준 뒤 신규 UserContent를 INTERESTED로 저장하고, 이미 같은 content_id가 있으면 기존 UserContent에 Source만 연결한다.

이미지·목록 가져오기는 위 Share Input 파이프라인과 별도 입력 어댑터를 사용하지만, Candidate Extraction 이후 Provider Verification → Entity Resolution → Decision → Feedback은 동일한 공통 파이프라인을 재사용한다.

8.2 AI 사용 원칙

  • AI는 존재하지 않는 콘텐츠를 만들어 DB에 넣지 않는다.
  • 공유 문맥에서 타입·제목·제작자 후보를 추출하고, 여러 실제 DB 후보를 랭킹하는 역할로 제한한다.
  • 최종 자동 확정은 외부 DB에서 실제 엔티티가 확인되고 증거 점수가 기준을 넘은 경우만 허용한다.
  • 작품명이 없는 “박찬욱 작품 중 이게 제일 좋음” 같은 문장은 사람 이름만으로 특정 영화를 추측 저장하지 않는다.

9. 직접 기록·검색 기반 메타데이터 자동완성

직접 검색은 기능정의서의 SCRAP-01 > + 저장과 자동 인식 실패 보완 경로다. 사용자는 제목 몇 글자만 입력해 후보를 선택하고, 저자·아티스트·감독·출판사·발매일·표지·외부 식별자 등은 Provider 결과로 자동완성한다. 신규 저장은 기본 INTERESTED이며, 이미 존재하는 동일 content_id는 재사용한다.

원칙
사용자가 메타데이터를 일일이 입력하게 하지 않는다. 직접 기록은 “검색어 입력 → 후보 선택 → 자동완성 → 상태 저장”의 짧은 흐름으로 처리하고, 외부 공유와 동일한 Content 엔티티에 연결한다.

9.1 기본 UX

제목 입력 → 콘텐츠 유형 추정/선택 → Provider 검색 → 후보 3~5개 → 1탭 선택 → 메타데이터 자동완성 → UserContent 상태 저장
유형사용자 입력 예자동완성 항목후보 구분 기준

9.2 책은 작품(Work)과 판본(Edition)을 분리 가능하게 설계

동일 작품이 여러 출판사·번역·개정판으로 존재하므로 사용자 경험은 작품 중심으로 단순하게 보여주되, 내부 데이터는 판본을 구분할 수 있게 설계한다. MVP에서는 ISBN 단위 Provider 레코드를 우선 저장하고, 정규화된 제목·저자 기준으로 동일 작품 후보를 묶을 수 있도록 work_key 또는 별도 Work 엔티티 확장 여지를 둔다.

Work: 데미안 / 헤르만 헤세
 ├─ Edition A: 민음사 / ISBN ...
 ├─ Edition B: 문예출판사 / ISBN ...
 └─ Edition C: 기타 출판사 / ISBN ...

MVP에서 판본 선택을 강제하지 않는다. 사용자가 특정 ISBN·서점 링크에서 유입된 경우에는 해당 판본을 연결하고, 제목 검색만 한 경우에는 대표 후보를 선택하게 한다.

9.3 외부 공유와 직접 기록은 같은 데이터로 합친다

직접 기록으로 생성된 콘텐츠와 Instagram·Threads·블로그·서점 공유로 생성된 콘텐츠를 별도 목록으로 관리하지 않는다. ProviderIdentifier와 정규화 필드를 이용해 동일 Content로 매칭하고, 사용자의 상태만 UserContent에서 관리한다.

직접 검색검색어 → Provider 후보 → 사용자 1탭 선택 → Content → UserContent
외부 공유Source → 후보 추출 → Provider 검증 → Content → UserContent
이미지 가져오기ImportCandidate → Provider 검증 → IMPORT-02 확인 → Content → UserContent
중복 시새 Content/UserContent는 만들지 않는다. 별도 시점의 의도적 저장이면 Source/Evidence + counted SaveEvent를 추가하고 save_count를 갱신한다. 동일 Batch/재시도 중복은 counted=false 또는 dedupe로 제외한다.

9.4 자동 확정보다 후보 선택을 우선

제목이 유일하고 Provider 결과가 명확할 때는 자동 선택할 수 있지만, 동명 작품·여러 판본·리마스터/재발매처럼 복수 후보가 존재하면 자동 확정하지 않는다. 사용자가 후보 카드 1개를 탭하면 필요한 메타데이터가 모두 채워지는 방식으로 정확도와 입력 편의성을 함께 확보한다.

10.1 월간 기록·연도별 경험 수 집계 규칙

핵심 원칙
월간 기록과 연도별 경험 수는 별도의 수기 통계 테이블을 source of truth로 두지 않는다. 저장은 SaveEvent, 경험 완료는 UserContent.completed_at / completed_local_date를 기준으로 집계한다. MVP 트래픽에서는 조회 시 계산해도 되고, 성능 문제가 생기면 동일 규칙으로 캐시/집계 테이블을 추가한다.
지표정의주의사항
월간 저장한 콘텐츠 수선택 월에 is_counted=true인 SaveEvent가 1회 이상 존재하는 고유 content_id 수같은 콘텐츠를 같은 달 5번 저장해도 상단 저장 수에서는 1개. 반복 5회는 관심 강도 데이터로 별도 사용.
월간 경험한 콘텐츠 수completed_local_date가 선택 월에 속하는 EXPERIENCED 고유 content_id 수‘시작’이 아니라 최종 감상 완료 기준.
월간 카테고리 완료 수선택 월 완료 콘텐츠를 Content.type = BOOK / ALBUM / MOVIE로 group byTRACK은 별도 콘텐츠 완료 수로 세지 않음.
주차별 경험 수선택 월 completed_local_date를 월내 주차 버킷으로 묶은 완료 수주차 정의는 월요일 시작 기준으로 통일. 월 경계 밖 날짜는 해당 월 그래프에서 제외.
월간 경험 콘텐츠 목록completed_local_date가 선택 월에 속하는 EXPERIENCED 콘텐츠completed_at DESC로 정렬해 표지/커버, 제목, 유형, 완료일을 표시한다.
연도별 총 경험 수completed_local_date의 연도가 선택 연도인 EXPERIENCED 고유 content_id 수숲 기록 목록과 연도별 숲 상세의 ‘n개의 경험’에 동일하게 사용.

10.2 기간 경계·타임존 규칙

  • 이벤트 저장: 서버에는 UTC timestamp를 저장하고, 발생 당시 사용자 로컬 날짜를 occurred_local_date / completed_local_date로 함께 확정한다.
  • 이유: 사용자가 이후 해외 이동·타임존 변경을 해도 과거 월간 기록과 연도별 경험 수의 날짜 버킷이 바뀌지 않게 한다.
  • 경험 완료: 최종 감상 완료 액션 시 completed_at과 completed_local_date를 같은 트랜잭션에서 기록한다.
  • 중복 완료: 이미 EXPERIENCED인 동일 UserContent에 대해 완료 버튼 재시도로 completed_at이 바뀌지 않도록 idempotency를 적용한다.

10.3 올해의 숲 / 숲 기록 데이터 규칙

화면조회 기준렌더링 원칙
올해의 숲현재 연도 completed_local_date 기준 EXPERIENCED 전체 + 현재 status=IN_PROGRESS 콘텐츠완료 콘텐츠는 큰 나무, IN_PROGRESS는 현재 성장 상태로 렌더링한다. 숲 아래 카테고리 요약은 EXPERIENCED를 BOOK / ALBUM / MOVIE로 집계한다. 최근 완료 1~2개는 completed_at DESC로 조회한다.
숲 기록 목록현재 연도를 포함해 completed_local_date가 1개 이상 존재하는 연도현재 연도는 현재 테마 + 실시간 총 경험 수를 사용하고, 종료 연도는 ForestYearSnapshot의 forest_theme_id / theme_version / representative_image_ref와 연도별 총 경험 수를 사용한다.
숲 기록 상세선택 연도. 현재 연도는 현재 테마 + 실시간 완료 집계, 종료 연도는 ForestYearSnapshot + 연도별 총 경험 수가로형 숲 장면 asset을 화면 대부분에 표시하고 드래그/스와이프로 좌우 pan한다. 화면 하단에는 연도별 총 경험 수만 표시한다. 개별 나무 선택용 좌표 데이터는 요구하지 않는다.
연도 종료 처리
연도 변경 시 과거 숲을 별도 콘텐츠 DB로 복제하지 않는다. 해당 연도 완료 UserContent는 그대로 두고, ForestYearSnapshot에 forest_theme_id / theme_version을 고정한다. 가로형 숲 장면 asset는 연말 배치, 사용자의 첫 ‘숲 기록’ 진입 시 lazy generation, 또는 클라이언트 렌더 후 업로드 중 한 방식을 선택할 수 있다. MVP에서는 구현 복잡도가 낮은 방식으로 시작하되, 재생성 시 항상 동일 theme_version을 사용한다.

11.3 Confidence

  • 0.90 이상 + 상충 증거 없음: canonical 매칭 자동 확정. 유입 경로별 확인 화면/저장 규칙은 별도 적용.
  • 0.65~0.89: 후보 1~3개 사용자 확인.
  • 0.65 미만 또는 후보 충돌: 직접 검색 / 최소 수정.

Confidence는 LLM의 자기평가값이 아니라 SourceEvidence와 Provider 검증 결과를 조합한 점수로 계산한다. 임계값은 초기값이며 실제 사용자 보정 로그로 재조정한다. 자동 확정률보다 오답 자동 매칭률을 우선 관리한다.

11.4 이미지 Batch 중복·저장 규칙

  • 한 이미지 안에서 같은 작품이 반복 검출되면 ImportCandidate 단계에서 먼저 묶는다.
  • 여러 이미지에서 같은 작품이 검출되어도 최종 Content/UserContent는 1개만 유지한다. 같은 ImportBatch 안에서는 해당 content_id의 SaveEvent도 1회만 counted 처리한다.
  • IMPORT-02에서 같은 user_id + content_id가 이미 있으면 신규 UserContent를 만들지 않고 Source/Evidence와 SaveEvent를 추가한다. 동일 Batch 중복이 아니라면 save_count를 1 증가시킨다.
  • 기존 UserContent 상태는 새 이미지 가져오기 때문에 자동 변경하지 않는다. 특히 EXPERIENCED를 INTERESTED로 되돌리지 않는다.
  • Batch 안의 한 항목이 실패해도 다른 항목의 저장을 막지 않는다.
  • 낮은 신뢰도 항목은 후보 교체·직접 검색·제외 중 하나로 처리한다.

13.1 실제 작동 검증용 샘플 세트

14. MVP 구현 순서

  1. 공통 스키마 확정: Content / ProviderIdentifier / UserContent / SaveEvent / Source / ImportBatch / SourceAsset / ImportCandidate / SourceEvidence / MatchLog / OnboardingProgress / ExperienceSelectionEvent / ForestYearSnapshot / ForestThemeDefinition
  2. ONB 데이터 규칙: 직접 응답 + IMPORT 저장 확정 항목을 유효 신호로 합산, 건너뛰기 제외, 10개 이상 완료

  4. IMPORT-02 1차 vertical slice: 책 장바구니·보관함 → 다건 추출 → Kakao/Google Books 검증 → 항목별 확인 → 일괄 INTERESTED 저장
  5. 직접 검색: 제목 입력 → Provider 후보 → 사용자 선택 → Content/UserContent 중복 병합
  6. Kakao 책 검색 API + Google Books fallback 품질 테스트
  7. MusicBrainz 검색·Release Group/Release 매핑 + 요청 큐·캐시
  8. Cover Art Archive 커버 연결, 커버 미존재 placeholder 처리
  9. TMDB 기술 연동 샘플 + KOBIS 보조 및 상용 조건 확인
  10. SHARE-01~03: 실제 iPhone Share Sheet payload 수집 → Source parser → 후보 추출 → 고신뢰 SHARE-02 / 확인 필요 SHARE-03
  11. OG / JSON-LD / 공개 메타데이터 파서
  12. 공통 Candidate Extraction / Provider Verification / Entity Resolution 모듈로 SHARE·IMPORT·직접 검색을 통합
  13. AI는 BOOK/ALBUM/MOVIE + title + creator 후보 구조화와 후보 랭킹에만 사용
  14. 중복 정책 구현: 동일 user_id + content_id는 UserContent 1개, 새 유입으로 기존 상태 자동 변경 금지
  15. 반복 저장 집계: SaveEvent dedupe/idempotency 구현, 같은 ImportBatch 중복 제외, save_count / first_saved_at / last_saved_at 갱신

  17. TODAY-02 데이터: SONGLIM_RECOMMENDATION / USER_DIRECT 선택 출처 이벤트 구분 기록
  18. 기간 집계 공통 모듈: SaveEvent.occurred_local_date + UserContent.completed_local_date 기준 월 필터, 월간 unique 저장 수, 완료 수, 카테고리/주차 group by, 연도별 총 경험 수 집계 구현
